# Feedback — ENS

First-hand only. Evidence per item. What worked as well as what didn't.

## 1. Emancipation works exactly as documented, on the first try
**What happened:** Ran `scripts/spikes/ensv2-sepolia-emancipation.sh` against the live Sepolia ENSv2 deployment. Deployed a throwaway `UserRegistry` proxy via `VerifiableFactory.deployProxy`, granted the deployer the four "dangerous" roles (`ROLE_SET_PARENT`, `ROLE_UNREGISTER`, `ROLE_SET_SUBREGISTRY`, `ROLE_SET_RESOLVER`) plus their admins, confirmed `isEmancipated()` read `false`, called `revokeRootRoles`, confirmed `isEmancipated()` flipped to `true`, then confirmed re-granting any role afterward reverts with `EACCannotGrantRoles` — no admin role survives to undo it. Matches the docs' description exactly, no surprises.
**Evidence:** Proxy `0x6a436e5eee7a5aca30db87267e0e0488a8e2f2fd`, deploy tx `0xc8fcd6c5d270506ba5b1e6d0597ed984b6bafa05ed0df5ac6514468045167fd4`, revoke tx `0xc8a950c20b590cd61ffe29495e2209daedea208c05e048f94b5abae51a4e155e` (block 12072481, Sepolia).
**Suggestion:** The Permissioned Registry and Enhanced Access Control docs pages never show a full runnable ABI (no `parseAbi()` block, no linked ABI JSON, no npm package) — every function signature has to be pieced together from prose across three separate pages, and the `Grant` struct's field order isn't documented at all. Had to pull the verified ABI from Sourcify directly to confirm `Grant{address account, uint256 roleBitmap}` field order before this would run safely. A single runnable code example per page (even just a `parseAbi` array) would save real time.

## 2. `isEmancipated()`'s real bitmap doesn't match the docs' "four dangerous roles" framing — found it almost too late
**What happened:** Spike 1 (above) revoked `ROLE_SET_PARENT`, `ROLE_UNREGISTER`, `ROLE_SET_SUBREGISTRY`, `ROLE_SET_RESOLVER` (+ admins) and `isEmancipated()` correctly flipped to `true` — so it looked complete. Pulling `RegistryRolesLib.sol`'s actual source via Sourcify for the real tree build showed `UNEMANCIPATED_ROLE_BITMAP` is actually `ROLE_CAN_TRANSFER_ADMIN | ROLE_SET_SUBREGISTRY(+ADMIN) | ROLE_SET_RESOLVER(+ADMIN) | ROLE_UNREGISTER(+ADMIN) | ROLE_UPGRADE(+ADMIN)` — it does **not** include `ROLE_SET_PARENT`, but it **does** include `ROLE_UPGRADE`/`ROLE_UPGRADE_ADMIN` and `ROLE_CAN_TRANSFER_ADMIN`, neither of which spike 1 touched. Spike 1's `isEmancipated()` only read `true` because its throwaway test proxy never held those two roles in the first place (default 0, so the AND-check passed trivially) — on a registry that's actually bootstrapped with a broad "take every role" grant (the pattern the ENS Drive/Cascade guide itself recommends for a registry you deploy and configure yourself), this would have left it genuinely upgradeable after "emancipation." Caught before touching real Sepolia by rehearsing the real `pypi.shankh.eth` build on an Anvil fork first and testing the corrected bitmap with a real `grantRootRoles` regrant attempt (reverts with `EACCannotGrantRoles`, confirmed) rather than trusting `isEmancipated()`'s boolean alone.
**Evidence:** `scripts/ens/register-tree-fork-rehearsal.sh`, steps 4–5; fork run log shows `isEmancipated()` false→true and the regrant attempt reverting with `EACCannotGrantRoles(0, <bitmap>, operator)`.
**Suggestion:** Document `UNEMANCIPATED_ROLE_BITMAP`'s exact composition on the emancipation/"root roles" docs page itself, not just in source — a worked example showing which roles must be revoked for a registry that was bootstrapped with every role (not just the four named in prose) would have caught this on the first pass instead of the second.

## 3. Per-text-record-key resolver scoping works exactly as `grantSetterRoles` implies — confirmed live
**What happened:** `plan-2.md`'s own design flagged this as unconfirmed before deploying the real tree. A prior ENSv2 project's reference notes named the exact mechanism (`grantSetterRoles` with placeholder setter calldata); this session confirmed it for real against Shankh's own case rather than taking that on faith: deployed a resolver taking broad `SET_TEXT`/`SET_TEXT_ADMIN` at init, used `grantSetterRoles(encodeFunctionData("setText", [placeholder, key, placeholder]), account)` to scope `shankh.source` to the maintainer and `shankh.revoked` to a freshly-deployed `KillSwitch` contract separately, then revoked the broad root grant. Result: the maintainer could still write `shankh.source` (the key-scoped grant survives a root-level revoke — confirms "a check is root ∪ the resource" works as documented) but got `EACUnauthorizedAccountRoles` writing `shankh.revoked` directly; `KillSwitch.revoke()` wrote `shankh.revoked` successfully, read back correctly via the real ENSIP-10 `resolve()` path.
**Evidence:** `scripts/ens/register-tree-fork-rehearsal.sh`, steps 7–10.
**Suggestion:** n/a — this worked exactly as the role model's own rules predict, once the right function (`grantSetterRoles`, not a direct role grant) is found. The function itself could be easier to discover — it's not obviously named for what it does ("setter roles" for a key, not an account's general roles) in the function list.
