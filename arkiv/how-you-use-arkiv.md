# How you use Arkiv — Shankh

**Do the things you filter on, who can edit each entity, and when it expires fit what your app does?** A watcher's question is "has anyone I trust found something wrong with a build I have installed?" — so `shankh.report` is read by **creator**: `shankh scan --trust` asks Arkiv for each trusted reporter's most recent reports (`.createdBy(wallet)`, sorted newest first), then matches `package`/`version`/`artifactSha256` (the build fingerprint) against what's installed, locally. It never asks Arkiv about a package by name, so the query reveals nothing about what's installed. Only the reporter's wallet can write a report, and Arkiv records that wallet as the creator — we trust that field, never the self-declared `reporter` attribute. Once written, nobody can edit it: every alarm is created `readonly` (an edit attempt by its own owner was refused live), while `permissionlessExtension` lets any machine that confirms it extend its lifetime. Which wallets count is published on ENS (`<name>.reporters.shankh.eth` → `shankh.signer`, writable only by the reporter). ~90-day expiry matches how long a given package version stays installed in the wild; `shankh.request` (24h, schema only so far) is a short-lived "has anyone checked this yet?" signal, not a permanent record.

**Does each Arkiv feature you use change something your users see?** Yes, live today: when a trusted reporter's alarm names a build installed on your machine, `shankh scan` re-checks it locally and, if it holds up, reports that build COMPROMISED and exits non-zero (proven live with two throwaway environments — `scripts/demo-arkiv.sh`, entity `0xe7d2102e…` in docs/evidence.md). An alarm that doesn't hold up locally is ignored; one that does is kept alive — the confirming machine posts its own confirmation and extends the original alarm with its own wallet (live: machine B's wallet `0xD7290D56042105e64FF16BE6CACC2da6E958bC5c` extended machine A's alarm `0x6a1c8ffc71…`). The status page also reads live `shankh.report` entities on every request. `shankhd`, the background watcher, runs that loop continuously and posts its own findings when it catches a new install by rebuilding it (live: entity `0x574edd31…cf10`). And the action the user ultimately sees is live too: on a confirmed alarm, the AWS keys registered with Shankh are quarantined and switched off.
